## Opt-in editor performance observations

Run `scripts/profile-gui.ps1 -Project 'C:/path/session.cleanslate' -Scenario 'locked-follow-background' -Report 'C:/existing-directory/new-report.json'` for a separate GUI-development project copy. The wrapper builds through the shared settings, labels the scenario, records the source commit (with a dirty suffix when applicable) and hashes the built executable. Coordinate the shared target so another branch does not rebuild it between capture build and launch. Existing report files are refused. Close the captured window normally to write its one JSON report; a forced termination does not produce a completed report. The prior GUI and owner source/project files are retained.

Repeat with a fresh report path for idle, playback, locked-follow, middle-pan, zoom and sound-edit scenarios, with and without import/analysis work. Keep project, zoom, logical size, appearance and device settings comparable. Include an idle period to detect observer-induced redraws; the observer uses a passive raw-event filter returning no application messages and requests no timer or redraw. The report stores no keys, text, project paths or audio contents. Input events are counted, and elapsed time from the latest observed input until the first waveform/gain canvas draw completes is reported; this is neither hardware input latency nor whole-window presentation completion.

Reports retain the most recent 4,096 durations per named boundary, plus lifetime observation and overwritten-sample counts. Median/p95/p99 use the nearest-rank empirical percentile of that retained window; max also refers to the retained window. Application update and canvas/cache preparation are wall-clock elapsed spans on their executing thread, including scheduling delays. Redraw-request intervals come from Iced's `RedrawRequested` timestamps and must not be called presented FPS or monitor refresh. Cache-build observation counts count actual cache closures, including ruler/track canvases; their duration covers the closure body, with subsequent cache/renderer conversion included only in the whole canvas-draw span. Canvas-draw counts also include cache hits. Collection itself adds bounded timer/lock overhead and can perturb observations; compare like-for-like capture builds.

Window logical dimensions and scale-change events are reported when observed; an unobserved scale remains null. Source/hash fields are launcher-provided identity, not embedded artifact attestation. GPU busy/presentation, physical input-to-photon/acoustic latency, process CPU/memory and callback deadlines are explicitly unavailable from this recorder. Use a separately labeled OS CPU/working-set sampler, About graphics diagnostics and the existing playback probes alongside it. A working-set sample maximum is not a guaranteed process-memory peak. Existing preview/editor benchmarks and `probe-pan.ps1` complement these observations but remain headless/software-geometry measurements. They do not substitute for a native editor scenario.

## Hot reload assessment

Iced 0.14 supports experimental hot reload through `iced/hot` and `cargo-hot`. Its documented limitation is patching the root crate. Our executable delegates to `rust_app::app::run()` and the GUI lives in the library target. The current cargo-hot source selects the binary/example target and reruns its rustc invocation for patches. That makes ordinary library GUI edits a poor fit for the documented path. No runtime hot-reload trial or new dependency was added; a separate executable UI boundary would need investigation before adoption.

Sources: [Iced hot-reload documentation](https://github.com/iced-rs/iced/pull/3000), [cargo-hot implementation](https://github.com/hecrj/cargo-hot/blob/master/src/main.rs), [Cargo build performance](https://doc.rust-lang.org/cargo/guide/build-performance.html).
