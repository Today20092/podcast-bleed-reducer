# Plugin GUI framework comparison (101)

Researched 2026-10-27 for [ticket 101](../../.scratch/offline-supervised-editor/issues/101-plugin-gui-framework-and-vendor-stack-research.md). Documentation and installed dependency metadata only: no framework download, build, prototype, native host, vendor installation or migration. Vendor binary identification is a separate evidence lane.

## Recommendation

**Keep egui 0.37 + nice-plug-egui 0.6 + nice-plug 0.4.2 for the current delivery.** Correct layout, typography/font coverage, clipping, input and redraw behavior in the existing editor. Old PNG mockups and clipped controls establish implementation/design problems, not an inability of egui to draw a polished audio interface. No evaluated source establishes that replacing the toolkit automatically improves appearance, frame pacing or memory use.

If a concrete limitation remains after those fixes, the smallest useful comparison is **one Iced editor screen through nice-plug-iced**, retaining the current Rust DSP, parameter/state IDs and format wrappers. That native adapter already exists. For a deliberate C++ product direction, **DPF/DGL** deserves the first multi-platform permissive comparison; **iPlug2/IGraphics** is another strong audio-focused candidate, but its Linux/platform and accessibility gaps matter. **VSTGUI** is also permissive and audio-focused, but would require a new Rust/C++ GUI bridge and CLAP attachment work. **JUCE** is capable, but introduces a copyleft/commercial licensing decision and C++ migration; **Slint** introduces a new integration/licensing decision and is not a demonstrated drop-in nice-plug replacement.

These are maintainability judgments from documented integration surfaces, not performance benchmarks. Migration has not been selected or authorized by this research.

## Licence decision

“Free to use,” “open source,” “permissive,” and “included plugin formats” are separate properties. Existing MIT code can remain MIT when used with copyleft code, but that does not make distribution of the combined binary MIT-only.

## Accessibility and testing

**Iced version compatibility is promising but untested.** The desktop manifest currently uses `iced = 0.14.0` (with advanced/canvas/svg features) and `iced_tiny_skia = 0.14.0`. The [official crates.io dependency response for nice-plug-iced 0.5.0](https://crates.io/api/v1/crates/nice-plug-iced/0.5.0/dependencies) declares `nice-plug-core ^0.4.2`, `iced_baseview ^0.6.0`, and Iced internal crates `^0.14`. [iced_baseview 0.6.0 dependencies](https://crates.io/api/v1/crates/iced_baseview/0.6.0/dependencies) likewise use Iced `^0.14` components and baseview `^0.4.1`. That lines up with the existing nice-plug 0.4.2 and desktop Iced generation, but no candidate lockfile, compile or runtime bridge was checked. Reuse of view/data logic is plausible; direct reuse of the desktop winit Application, renderer/window ownership or every custom widget is not demonstrated. This exact-version metadata is more useful than the inconsistent cached `latest` doc pages.

Native accessibility is an integration property, not a screenshot property. [JUCE AccessibilityHandler](https://docs.juce.com/master/classjuce_1_1AccessibilityHandler.html) documents roles, actions and value/text interfaces. iPlug2's [maintainer stated on 2026-02-27](https://github.com/orgs/iPlug2/discussions/1332) that the default GUI does not currently support screen readers; keyboard workarounds are not equivalent to an accessible control tree. Equivalent complete VSTGUI screen-reader coverage was not established in this bounded pass.

egui has [AccessKit-based kittest and snapshot tooling](https://docs.rs/egui_kittest/0.37.0/egui_kittest/), including accessible-name checks. That supports headless widget/layout regressions, **not** proof that the baseview plugin bridge exposes a working OS screen-reader tree. The [baseview accessibility issue](https://github.com/RustAudio/baseview/issues/200) makes this distinction explicit; current pinned behavior still needs checking. Do not describe current CleanSlate accessibility as complete. Iced plugin keyboard focus, text entry and assistive-technology behavior also require adapter/host checks, not inheritance of standalone claims.

Slint documents [accessible custom properties/actions](https://docs.slint.dev/latest/docs/slint/reference/common/) and [system-test input/screenshot tooling](https://testing.slint.dev/api/window/). A custom plugin backend must preserve those paths; this research did not verify that AURA/nice-plug integration does. For every choice, unit/render tests complement actual VST3/CLAP open/close, automation, DPI, focus and resize tests; no alternate framework is exempt.

## Format and SDK boundaries

GUI rendering, format adapters and host support are three different layers. The current [VST3 SDK licence](https://github.com/steinbergmedia/vst3sdk/blob/master/LICENSE.txt) is MIT; [CLAP](https://github.com/free-audio/clap/blob/main/LICENSE) is MIT. Neither says that a GUI toolkit implements their editor lifecycle correctly. iPlug2/JUCE advertising VST2 targets does not establish that this project possesses the required legacy SDK rights. Steinberg's [SDK discontinuation notice](https://forums.steinberg.net/t/vst-2-sdk-discontinued/201774) and [official reply about VST2 licensing](https://forums.steinberg.net/t/permission-to-develop-vst2-host-that-will-never-be-distributed/202042) are separate from VSTGUI's permissive licence. Existing ticket 97 must resolve the actual adapter/licensing/host path; this research neither selects one nor claims OBS compatibility.

## One-screen comparison, only if separately selected

Start by correcting the current implementation. If a specific blocker remains, compare the **same Podcast screen in egui and nice-plug-iced**, using the same fake/immutable waveform and meter data. Include two waveform lanes, selection/zoom, speaker/room-label popup, readiness/stale status, one parameter with host gestures, and advancing meters. Reuse owned fonts/icons, not vendor assets. Keep DSP and persistent/format identities unchanged.

Prototype acceptance should be concrete:

1. Actual embedded VST3 and CLAP editor opens/closes repeatedly, reopens at saved size, resizes without clipping, and survives 100/125/150/200% DPI changes. Test text/icon/font coverage on the machine rather than judging only a PNG.
2. Pointer drag/capture, wheel/modifiers, keyboard navigation, text entry and host shortcut ownership work. Verify accessible labels/actions separately from visual output.
3. Selection, popup, waveform/meter updates and parameter automation retain meaning across editor reopen and state restore; no change to delivered audio, source validation or cancellation.
4. Compare measured full-frame p50/p95/p99, idle/animated CPU and private/resident memory at identical dimensions/data/update rates on this 32 GiB PC. Record renderer, host, scale and build identity. No numeric winner or FPS/RAM claim is available yet. Use one guarded job globally; no concurrent Rust/C++ builds or DAW profiling.
5. Retain the existing editor unless the alternative fixes the named blocker and demonstrably improves maintenance/usability without worse lifecycle/input/resource results. A prettier isolated sample is insufficient reason to migrate the product.

## Vendor-stack boundary and remaining unknowns

The [current FabFilter jobs page](https://www.fabfilter.com/jobs) says no openings and did not disclose a GUI framework. No first-party careers/developer source confirming an in-house toolkit was established here. Retained exact-hash REA findings, supplied by the parallel inspection lane, are the appropriate source for per-product native type/string evidence. `gui::OpenGLRenderer` or JUCE types can support a bounded stack identification; generic OpenGL imports cannot identify a complete toolkit or establish performance. The current egui path also has an OpenGL backend: shared graphics API is not shared implementation or visual quality.

Unmeasured here: comparative RAM/frame latency, native accessibility completeness, exact migration effort, Linux behavior of preview/unsupported paths and every candidate's host matrix. No framework is recommended on an invented performance ranking; ongoing ticket 96 fixes continue independently.
