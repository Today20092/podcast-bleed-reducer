# Plugin feasibility: solo OBS gate and offline DAW ownership

2026-10-23. Discovery for [ticket 67](../../.scratch/offline-supervised-editor/issues/67-live-clap-vst3-discovery.md), not an implementation specification. Code inspected at development source `d1c5b358a86c2b514c89f54534953424a69f0796`. No plugin, host compatibility or realtime performance test was run; no framework or dependency was selected.

## Two workflows

The owner's latest clarification separates **one solo microphone in OBS, processed as a smart voice gate**, from **DAW processing across several track instances**, calibrated from short speaking/reference sections selected and played using the DAW's existing waveform. No complete waveform UI inside the plugin is requested. The owner wants prototypes for both workflows, without ranking one first, and does not want an hour-long capture pass. The DAW workflow does not inherit OBS's realtime or 100 ms requirement, but preview playback still has processing deadlines. Earlier discussion of mandatory whole-recording capture is superseded by this clarification.

VST3's processing interface supplies **blocks on the instance's configured buses**, parameter/event queues and optional processing context. Offline processing changes the processing mode; it does not itself grant random access to complete source clips, other tracks, or all project audio. That last sentence is an architectural inference from the API contract, not a host test. Three instances receiving three streams are not automatically one synchronized multitrack analysis session. ## Current engine: facts from graph and source

Discovery used the indexed primary checkout, symbol search, an outbound trace from `analyze_acoustic_with_feedback`, and symbol snippets. Graph traces include some ambiguous short-name edges, so claims below rely on the fetched bodies rather than treating every graph edge as a proven call.

- `SessionOwnershipCache::analyze_acoustic_with_feedback` measures acoustic relationships, validates human references, obtains complete VAD probability arrays, trains per-track ownership models from selected truth rows, applies them across the recording, then revalidates before accepting the result. It binds models to source/track/reference identities. [Source](../../src/session_ownership.rs#L269).
- `AcousticEvidenceCache::analyze` verifies analysis files by hash, requires alignment and usable solo/room references, builds fixed joint measurements, fits directed transfers and computes residual features. `SessionAcoustics::features_at` uses all tracks' same-time levels and pair evidence. The fitted transfer is evidence for ownership, not an audio subtraction output. [Analysis](../../src/acoustics.rs#L171), [features](../../src/acoustics.rs#L94).
- The current direct-16 kHz Silero path consumes 512-sample frames (32 ms), with recurrent state handled by its frame runner; preparation reads files and allocates probability/energy arrays. A frame size is not measured end-to-end latency. [VAD preparation](../../src/vad.rs#L231).
- `JointFacts::prepare_blocks` measures 32 ms acoustic frames, estimates a pair lag across each 256 ms block, and uses neighboring frames for correlation. It also derives whole-recording quantiles/automatic leakage facts; supervised acoustic floors subsequently use room labels. Thus exact reuse of the existing block evidence is not a causal 32 ms streaming operation. Not every whole-recording field is necessarily consumed by the supervised path. [Source](../../src/joint_detector.rs#L96).
- `TemporalOwnershipCache::optimize_evidence` applies per-track hysteresis and preserves missing-evidence regions. The project-aware path additionally applies human truth. `AutomaticEnvelope::from_ownership` requires ordered complete timeline coverage, merges bounded gaps and places opening fades before the next preserved span. Those future-dependent choices suit offline analysis; a gate needs an explicitly bounded streaming policy. [Temporal code](../../src/temporal_ownership.rs#L259), [hysteresis](../../src/temporal_ownership.rs#L427), [current automatic envelope](../../src/effective_envelope.rs#L193).

The existing ownership/envelope architecture is a plausible reuse boundary for offline DAW analysis **after complete aligned sources and references exist**. Its file/source binding assumptions require an adapter and new host/session identity rules; blindly calling existing preparation from an audio callback is unsuitable. Steinberg explicitly directs plugin processing code to avoid allocation in its realtime processing thread. [VST3 threading documentation](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/API+Documentation/Index.html?highlight=threading).

Scalar gain affects every component mixed into a microphone together. Consequently the present attenuation-only path can reduce between-phrase noise or attenuate a non-owning microphone, but cannot selectively remove another speaker's leakage while preserving the wanted voice in the same simultaneous samples. This follows from the current gain architecture, not a listening-quality judgment. [Architecture contract](../adr/0006-offline-supervised-editable-envelopes.md).

## DAW short-reference calibration, then playback inference

**Feasibility inference:** short examples can supply the calibration/training inputs; they do not supply an already analyzed whole recording. The current model is fitted from labeled truth rows, room floors from room labels, and transfer qualification from solo reference samples with separate training/validation portions. Therefore there is no demonstrated mathematical need to listen to every unlabelled sample before fitting that calibration. However, the current API couples fitting to file validation and whole-timeline feature/probability passes. Separating fit from application is engineering work, not an existing supported entry point. [Training rows and application pass](../../src/session_ownership.rs#L269), [reference sampling](../../src/acoustic_transfer.rs#L31), [transfer qualification](../../src/acoustic_transfer.rs#L77).

| Current dependency | Can short-reference capture replace it? | Result-equivalence condition / limitation |
| --- | --- | --- |
| Solo/room labels, room medians, transfer fit/validation and logistic training examples | In principle, yes: capture all grouped inputs during each labeled selection, with boundary/context guards. | Preserve the actual sample data, label times, selected training rows, feature block origin and fit rules. Concatenating unrelated snippets into one recording would create false adjacency and alter context. |
| Full probability/acoustic arrays and final source hashes | These are current orchestration/storage contracts, not proof that training requires all unlabelled audio. | New capture/session identities and a fit/infer boundary are required. Partial capture cannot be marked complete current-app analysis or trusted as the whole source. |
| Per-frame relative dominance, pair correlation and transfer residual evidence | Must still receive synchronized inputs from every grouped microphone during future processing. | An instance with only its own microphone lacks those competing-track features. [Feature assembly](../../src/session_ownership.rs#L606), [cross-track features](../../src/acoustics.rs#L94). |
| Acoustic correlation window | Requires the relevant 256 ms block and neighbor frames, including future samples for earlier positions. | Preserve the absolute block/frame grid for parity; starting a new grid at every seek changes features. [Joint blocks](../../src/joint_detector.rs#L96). |
| Transfer residual features | Can be computed in bounded blocks with guarded neighboring samples after calibration. | Current lag can address samples on either side of the current position; keep both guards and exact sample/grid policy. Current implementation still reads complete prepared sources into successive blocks. [Residual calculation](../../src/acoustic_transfer.rs#L203). |
| Silero recurrent state, ownership hysteresis, temporal/gain gap policy and pre-onset fades | Cannot be reconstructed identically from a bare arbitrary seek point plus a model. | Need retained/checkpointed state or preroll, future context and a documented cold-start/seek rule. Whole-file and seek-started processing must not be claimed identical without comparison. [Silero runner](../../src/vad.rs#L300), [temporal rules](../../src/temporal_ownership.rs#L427), [gain generation](../../src/effective_envelope.rs#L193). |

The `JointFacts` preparation also computes whole-recording quantiles/leakage estimates. In the supervised path inspected here, acoustic floors are replaced by labeled-room medians, directed fits use selected solo labels, and `SessionAcoustics::features_at` consumes levels/pairs/fitted reference data. Those automatic whole-recording statistics are not evidence that the supervised estimator fundamentally requires a full preliminary recording pass. A split must audit actual consumers and retain equivalence tests rather than replacing these statistics by intuition. [Preparation](../../src/joint_detector.rs#L96), [supervised acoustic fitting](../../src/acoustics.rs#L171).

**Cross-instance scheduling is the main host proof.** VST3 exposes per-call sample counts/buses and optional processing context; when context is supplied it contains project sample position. It does not specify that separate instances receive matching blocks before one must return. FL Studio documents threaded plugin processing and buffer-size options. Hence a design must not wait synchronously inside instance A's callback for B's same-time callback: a serial host schedule could prevent B from being called until A returns. This deadlock example is an inference from missing cross-instance ordering guarantees, not a measured host failure. A bounded shared queue/delay can absorb limited skew only after the host's delivery pattern is established; it cannot guarantee bounded memory or delay against arbitrarily far-ahead rendering of one branch. [VST3 block API](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/structSteinberg_1_1Vst_1_1ProcessData.html), [project timing and discontinuities](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/structSteinberg_1_1Vst_1_1ProcessContext.html), [FL wrapper](https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/plugins/wrapper.htm).

CLAP specifically warns that its steady-time counter may be instance-specific, and transport can be absent; equal callback numbers/steady-time counters are therefore not a general synchronization strategy. Match explicit session identity, timeline sample ranges, sample rates, generation and discontinuities, and establish whether the host actually supplies the needed timing. Separate process isolation is untested. [CLAP process contract](https://github.com/free-audio/clap/blob/main/include/clap/process.h).

Possible delivery shapes to prototype, without selecting one:

- **Grouped instances with deferred output:** keep the requested three inserts, collect timestamped blocks without blocking callbacks, compute a shared decision once sufficient cross-track context arrives, and return delayed matching audio. Requires host-specific scheduling, latency-compensation and offline-render tests; same plugin latency must be applied consistently. Data from a loop/restart/seek must never join the wrong generation.
- **One multichannel/sidechain analysis point:** route all unprocessed microphone inputs into a common decision point with separate per-track outputs or consumers. It makes cross-track delivery explicit in the host graph, but may conflict with the desired simple three-insert workflow and depends on tested host bus/channel support. This is a fallback question, not an accepted routing requirement.
- **Fast source acquisition:** verified random-access integration or a faster-than-realtime DAW render can provide source data for the unchanged offline engine. A bounce may be quicker than playback, but still traverses the selected audio and does not make data available merely because the user selected a waveform range. No cited generic plugin API lets an insert command all host tracks to render. The owner has rejected a mandatory real-time hour-long pass; ask only whether an explicit fast preparation operation is acceptable if grouped inference cannot meet host scheduling requirements. [ARA capability](https://github.com/Celemony/ARA_SDK/blob/main/README.md), [VST3 processing modes](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/namespaceSteinberg_1_1Vst.html).

DAW preview needs enough delay/preroll for future feature context, fade placement and state, even though it has no OBS latency budget. Offline bounce removes wall-clock audition pressure, but still needs correctly ordered/available samples and must honor the host API. A format's offline mode does not itself solve cross-instance readiness or give permission to stall awaiting an instance the host has not called. Exact current-app results on every arbitrary seek are a stronger contract than applying the same fitted classifier during continuous playback; decide and measure them separately.

For parity, define whether calibration/application input is the signal at each insert or original files. Gain/EQ/time edits before an insert can change features. Compare identical samples/references/settings for continuous playback first, then seeks, loops, changed block sizes, reopen and offline bounce. Report expected cold-start differences explicitly. The plugin need not draw a full timeline: the DAW can audition/select examples while the plugin captures and labels them, subject to verified host timing and an explicit reference-type action.

## OBS solo gate: separate bounded experiment

Proposal: after the owner confirms the desired sound and maximum added delay, test a single-input speech-aware gate with a short soundcheck, a bounded analysis queue, deliberate attack/release/lookahead and a preservation policy on late/invalid inference. Preserve quiet speech, onsets/endings and wanted reactions; measure missed deadlines and A/V synchronization. This does not require cross-instance podcast coordination. Continuing noise removal while speaking would require a separately accepted audio objective.

For a future format wrapper, CLAP documents activation-time memory preparation, sample-rate/block bounds and fixed active latency/ports; its latency extension reports samples and requires reactivation for changes. VST3 reports latency in samples and host notification can interrupt playback. These APIs enable reporting, not a performance guarantee. [CLAP lifecycle](https://github.com/free-audio/clap/blob/main/include/clap/plugin.h), [CLAP latency](https://github.com/free-audio/clap/blob/main/include/clap/ext/latency.h), [VST3 processor latency](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/classSteinberg_1_1Vst_1_1IAudioProcessor.html).

Current upstream CLAP and VST3 SDK root licenses are MIT; ARA SDK identifies Apache-2.0. A chosen pinned SDK/framework, wrapper, model/runtime and distributed binaries still need their own license inventory. No dependency choice or legal conclusion is made here. [CLAP license](https://github.com/free-audio/clap/blob/main/LICENSE), [VST3 SDK license](https://github.com/steinbergmedia/vst3sdk/blob/master/LICENSE.txt), [ARA SDK](https://github.com/Celemony/ARA_SDK/blob/main/README.md).
