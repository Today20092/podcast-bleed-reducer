# FabFilter performance lessons from primary sources

Date: 2026-10-21. Scope: official documentation for Pro-Q 4, Pro-L 2 and Pro-R 2, with one distinct workload-budget example from Twin 3. This is a candidate list for owner review, not an implementation specification or a set of approved tickets.

## What this evidence establishes

These sources describe product behavior and tradeoffs. They do **not** measure the installed builds, prove FabFilter is faster than CleanSlate, or identify a generally superior programming language. Current binary/runtime inspection and CleanSlate source profiling are separate evidence streams. A documented control is not proof of a particular internal implementation, cache, scheduler, allocation strategy, SIMD path, GPU compute pipeline or speedup.

No claim below establishes that FabFilter performs audio DSP on the GPU. Graphics acceleration and audio processing must be assessed separately. Staff forum statements are attributed and dated; other forum participants' anecdotes are excluded.

## Transferable candidates

Priority is a proposed investigation order. Check whether each mechanism already exists in CleanSlate before proposing work. Measurements below are scoped checks for a chosen improvement; they do not reopen the roadmap's previously waived formal benchmark gate.

| Priority / candidate | Documented FabFilter evidence | Possible CleanSlate application — inference, not a FabFilter implementation claim | Required check / limit |
| --- | --- | --- | --- |
| 1. Give visual work a separate budget | Pro-Q 4 exposes analyzer resolution: 1024/2048/4096/8192 points. Larger windows improve frequency precision but need more input samples and reduce spectrum update rate. Its **Speed** setting changes spectrum release behavior. [Spectrum analyzer](https://www.fabfilter.com/help/pro-q/using/analyzer) | Keep waveform/detail work proportional to visible pixels and zoom; update meters independently of expensive analysis. Reuse existing cached summaries where available. | Profile idle, playback, zoom and drag separately. Do not equate analyzer Speed, FFT update cadence and GUI frame rate. Do not change the authoritative envelope or audio result to save drawing work. |
| 2. Stop optional visual work when it has no consumer | Pro-R 2 offers analyzer Off; internal bypass stops its frequency analyzer and uses soft bypassing to avoid clicks. [Analyzer](https://prod.fabfilter.com/help/pro-r/using/spectrumanalyzer), [Input/output options](https://www.fabfilter.com/help/pro-r/using/outputoptions) | Avoid scheduling optional live meters/animations while their UI is hidden or inactive. Resume with a truthful current snapshot. | Verify hidden/minimized and stopped states. Preserve audio continuity, export behavior and any measurements that must accumulate. The docs do not prove every DSP path stops while bypassed. |
| 3. Use bounded visual history instead of unlimited display detail | Pro-L 2 has Slow, Fast, Infinite and Off display modes. Infinite increases history density as the display fills; Compact layout hides the history display in favor of meters. [Metering](https://www.fabfilter.com/help/pro-l/using/metering) | Keep an informative overview of a long recording by reducing display history to screen resolution. Offer an uncluttered listening view only if useful in the current workflow. | Check memory and drawing cost on long sessions. This describes visible density; the manual does not reveal FabFilter's storage structure or prove bounded internal memory. Avoid duplicating existing waveform LOD. |
| 4. Diagnose GPU/driver behavior before changing renderers | FabFilter documents GPU-accelerated graphics and a way to disable acceleration when certain GPU/host combinations cause problems. [Support FAQ](https://www.fabfilter.com/support/faq#how-can-i-disable-graphics-acceleration-on-my-computer) | Record the active graphics backend/adapter in useful diagnostics; investigate rendering problems across display scale and refresh rate before considering a fallback. | Measure frame time and GPU activity. A new renderer or a software fallback is not justified merely because FabFilter has an acceleration switch; evaluate support in the current stack first. Do not change the user's FabFilter registry settings as part of research. |
| 5. Treat interaction latency separately from throughput | Pro-Q 4's linear-phase resolution explicitly trades frequency resolution against latency. At 44.1 kHz, documented Low is about 70 ms and Maximum about 1509 ms; mixed L/R and M/S stages double latency. Pro-L 2 also documents algorithm-, lookahead- and option-dependent latency. [Q processing modes](https://prod.fabfilter.com/help/pro-q/using/processingmode), [L advanced settings](https://www.fabfilter.com/help/pro-l/using/advancedsettings) | Profile time to audible playback, seek and control feedback separately from whole-file analysis/export time. Preserve quick feedback even when long work is queued. | These are audio algorithm latencies, not GUI input latency. CleanSlate does not need a linear-phase EQ. Any optimization must preserve shared preview/export envelope evaluation and cancellation. |
| 6. Make expensive quality choices purposeful | Pro-L 2 says oversampling reduces aliasing but increases CPU and can introduce slight pre-ringing; it recommends 4x/8x for normal use and notes 16x/32x may suit offline rendering. [Oversampling](https://www.fabfilter.com/help/pro-l/using/oversampling) | If a future, demonstrated expensive algorithm needs distinct interactive/offline settings, explain its cost and audible effect clearly and validate both paths. | **No proposal to add oversampling to CleanSlate.** Gain envelopes do not inherit the limiter's nonlinear aliasing problem. Do not add speculative quality modes or silently make preview differ from export. |
| 7. Parallelize independent work with a measured concurrency limit | FabFilter's Frederik stated on 2021-11-11 that Pro-L 2 processing used one thread, while the host distributed plugin instances across tracks/cores. [Staff response](https://prod.fabfilter.com/forum/topic/6783/pro-l-x32-upsampling) | Investigate independent per-track/job work rather than assuming a larger thread count speeds one dependent processing chain. Bound workers so UI/audio retain time and memory stays reasonable. | Historical statement, not proof about today's installed build. Profile the current worker pool and critical path first. Total CPU percentage alone can hide a saturated deadline-critical thread. No SIMD or multicore implementation is established by these docs. |
| 8. Size workloads by actual work dimensions | FabFilter staff explained Pro-R CPU varies with preset/filter count/reverb length (2019); Pro-R 2 7.1.4 also involves cross-channel interactions (2024). Twin 3 documents a maximum voice budget and warns high voice counts increase CPU. [R staff responses](https://prod.fabfilter.com/forum/topic/3566/pro-r-high-cpu-usage), [Twin polyphony](https://www.fabfilter.com/help/twin/using/polyphonyandunison) | Use representative track counts, duration, sample rates and visible detail when comparing a proposed change. Bound concurrent analysis/decode work according to memory and foreground responsiveness. | CleanSlate's workload differs from a reverb or synthesizer. Do not extrapolate one stereo preset linearly to every track/channel configuration or add voice/quality controls to this app. |

## Supporting distinctions

- Pro-L 2 distinguishes **True Peak Metering** from **True Peak Limiting**. Its meter documents additional internal oversampling; displaying a measurement and changing the audio are different operations. Optional measurement cost should not be confused with the processing path. [Metering](https://www.fabfilter.com/help/pro-l/using/metering)
- Pro-L 2's own bypass promises latency compensation plus soft switching. Any comparison/listening-mode optimization should preserve alignment and click-free transitions, even if a hard toggle would be cheaper. [Input/output options](https://www.fabfilter.com/help/pro-l/using/outputoptions)
- Pro-R 2's VST documentation says VST3 is more CPU-friendly **in some cases**. That is a host/format-specific statement, not a universal CLAP/VST2/VST3 speed ranking and not a reason for a standalone application to adopt a plugin format. [VST versions](https://prod.fabfilter.com/help/pro-r/support/vstplugins)

## What remains unmeasured

Installed-version CPU/GPU use, frame cadence, audio callback deadlines, memory/allocation rate, idle/silence behavior, hidden-editor behavior, SIMD dispatch, internal worker topology and cache invalidation are unmeasured by this documentation review. DLL/import/disassembly evidence can suggest mechanisms; only a controlled runtime test can establish their activity and cost in a particular workload.

The strongest immediate candidates are targeted visual-work profiling, inactive-display scheduling and responsive foreground work. Quality-mode and DSP changes remain conditional ideas, not recommended additions. Owner selection and a source audit should precede scoped tickets.
