# Portable updater feasibility — ticket 73

Delivery update: the accepted Windows-first scope is implemented and checked on
development. See the [2026-10-23 delivery receipt](portable-updater-delivery-2026-10-23.md)
for actual results, signing bootstrap, hashes and remaining limits. The proposal
and discovery evidence below are preserved as historical design context.

Discovery date: 2026-10-23. This is a proposed implementation contract, not a completed updater or a release authorization. No package, dependency, signing key or release was changed during this investigation.

## Decision

The owner confirmed the Windows-first installation/manual-fallback boundary on 2026-10-23 after reviewing the proposal. Implementation and the signing bootstrap remain outstanding.

Build manual update checking for all advertised platforms and transactional installation only for a clean Windows x64 portable package on a writable local fixed NTFS volume. Other platforms, removable/network/read-only installations, legacy mixed folders and development executables receive the matching release download link and explicit manual instructions. No startup checks, unattended installation, elevation, project migration or automatic project reopening.

Use the existing complete ZIP and manifest rather than a single-executable updater. Add independently signed update metadata and a small recovery helper mode in the existing binary. Copy the **currently trusted** application and its required runtime DLLs into a separate transaction directory before shutdown; launch that copy in helper mode. It survives moving either installation and introduces no second product or script interpreter requirement.

This is larger than adding an HTTP button: recovery, release signing, safe shutdown and real packaged failure tests are delivery prerequisites.

## Release selection and network boundary

Register Check for updates through `src/shortcuts.rs` and existing menu/command dispatch. Show current version, offered version, release notes, and Download and install. Download/cancel/progress/errors run on a worker; the GUI thread never blocks. Manual checking is the only trigger, preserving offline startup.

Request the public repository releases API without a token; never ship a PAT or read ambient GitHub credentials. Page through a bounded list; reject malformed fields, draft releases, duplicate matching assets and conflicting tag/manifest/version identity. If the page/time budget is exhausted, report an incomplete check rather than claiming no update. Select greatest **semantic precedence**, not upload time or lexical order. Parse one leading `v`, require canonical SemVer and compare without build metadata.

Stable channel is the default even on an existing alpha installation: `0.1.0-alpha.8` can upgrade to `1.0.0`. Prereleases require an explicit per-check Include prereleases control; installing one never silently changes future checking policy. Compare release prerelease flag against parsed version. Same/older precedence is not an update; missing Windows package or signature means no installable update, with a useful release-page explanation.

GitHub's latest endpoint excludes draft/prerelease releases but orders according to its own release policy; use explicit selection for predictable SemVer behavior. Public unauthenticated API calls share an IP-based 60/hour primary limit. Honor rate-limit reset/Retry-After and stop on secondary limiting; no retry loop. See [release endpoints](https://docs.github.com/en/rest/releases/releases), [asset endpoints](https://docs.github.com/en/rest/releases/assets), and [rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

Constrain every request and every redirect **before following it**: HTTPS, normal port, no credentials, no downgrade; metadata only `api.github.com/repos/Today20092/podcast-bleed-reducer/...`; release download initially only `github.com/Today20092/podcast-bleed-reducer/releases/download/<expected tag>/<exact asset>`. Permit the release-delivery redirect host `release-assets.githubusercontent.com` only for a redirect from that validated download, with a bounded hop count. Do not allow arbitrary `*.githubusercontent.com` or URLs supplied by JSON. If GitHub changes delivery hosts, fail closed with manual download until reviewed. This proposed policy needs an integration fixture/live-host check before shipping; it is not a claim that GitHub guarantees one delivery hostname forever.

Promote the already locked `ureq` and `semver` to direct dependencies only in the corresponding build stage after version-specific validation. `ureq` documents configurable redirects/timeouts and streamed body readers; disable automatic redirects and validate each Location manually. Set connection/read/overall timeouts, metadata/body byte budgets and cancellation checks between chunks. SemVer's `cmp_precedence` ignores build metadata. Current upstream docs were fetched through Context7: [ureq configuration](https://github.com/algesten/ureq/blob/main/_autodocs/configuration.md), [ureq bodies](https://github.com/algesten/ureq/blob/main/_autodocs/api-reference/body.md), [semver](https://github.com/dtolnay/semver). API examples from current upstream are not proof every option exists in locked 3.4.0; confirm that before coding.

## Authentication and package contract

Use a Minisign detached signature over the exact bytes of a small, versioned `update-manifest.json`, with the release verification public key embedded in the application/helper. The signed descriptor binds repository/product ID, schema, version/tag, channel, platform, archive name, archive SHA-256, compressed bytes, maximum expanded bytes/file count and inner package-manifest SHA-256. The archive hash authenticates every archive byte; the inner manifest authenticates the owned inventory after extraction. Sign the exact UTF-8 bytes, not reserialized JSON. Reject unknown schema/algorithm/key IDs, duplicate JSON keys and any identity mismatch before replacement.

[Minisign](https://github.com/jedisct1/minisign) documents Ed25519 file signatures. Choose a maintained compatible Rust verifier and bounded ZIP reader in the first build stage after fetching their current documentation and checking maintenance/license/format behavior; neither is selected or installed by this report. Do not hand-write cryptography, invoke a downloaded verifier or use PowerShell Expand-Archive as the trust boundary.

The owner must establish an actual signing key outside the repository and distribute its public key with a deliberately trusted bootstrap build. Keep the private key outside ordinary package jobs; use a protected signing step/owner procedure over reviewed artifact hashes. A compromised signing key or trusted bootstrap remains a compromise; TLS, GitHub digest and a checksum beside the ZIP alone cannot provide independent publisher authentication. A key rotation needs a transition release carrying the next key authorized by the existing trust root; never fetch a replacement trust root from unsigned metadata. Existing 1.0.0 has no updater/trust key and must be manually replaced once with the bootstrap build. Missing signatures always disable automatic installation, including for older releases.

Extend existing package-manifest fields with schema/product/package-kind/file-size/entrypoint identity. Keep compiler/source evidence. The external signed descriptor binds the internal manifest without a self-hash cycle. Publication must verify all required signed descriptors/signatures before offering installation; retain `.sha256` files for manual users. Metadata generation, signatures, notices and workflow artifact patterns must change together.

Before extraction, validate complete ZIP directory metadata and each write: exactly one expected top-level folder; no absolute/drive/UNC paths, `..`, NUL, alternate streams, Windows device names, trailing-dot/space aliases, case-fold duplicates, symlinks/hardlinks/reparse points, special entries, file/directory collisions or unsupported encryption. Stream to create-new files under a fresh private staging directory; revalidate parents and disallow reparse ancestors. Enforce both signed and local hard ceilings (initial proposals: 1 GiB archive, 3 GiB expanded, 20,000 entries, 512 MiB single file; confirm against packaged artifacts). Enforce actual decoded bytes, not merely ZIP headers. Verify exact regular-file inventory and hashes; unexpected extras fail.

## Ownership and transaction

The first installer accepts only an exact, unmodified package tree matching its installed manifest, known package path grammar, and running executable identity. The root cannot be a drive root, user profile, data/cache root or a reparse path. Check ancestor identity and fixed local NTFS volume before staging; unsupported or uncertain storage is manual-only. A legacy tree with no manifest, modified owned files or **any unrelated extra files**, including projects/audio/exports, is manual-only. Explain that the owner should extract a new version to a new clean folder and leave the old mixed folder intact. Do not relocate/delete user files to make a folder eligible. This deliberate limitation avoids a per-file merge engine while preserving all user work.

For an eligible clean tree, stage the complete new tree in a fresh sibling transaction directory on the **same volume** as the installation. Preserve the existing installation directory name so shortcuts still work. Helper runtime, journal and backup live outside both candidate package roots. Check available space for archive + expanded tree + helper + safety margin; original tree becomes the backup by rename, not by destructive copy. A preflight is advisory: every real filesystem operation still handles failure.

1. Download, verify signature/archive/manifest and stage while the old app remains usable. Cancel removes only this verified transaction's temporary files.
2. Show the version and explicit restart choice. Resolve pending edits through Save/Discard/Cancel; wait for save success, no active gestures or dialogs, no pending import commit. Await analysis/export completion or user-confirmed cancellation **and worker acknowledgment**. Stop audition and verify a successful project save; failures keep the old session open. Hold a per-installation update lock and reject other running instances.
3. Copy and verify the old trusted executable plus its runtime DLLs to helper staging; create a private transaction nonce and canonical path identities. Persist and flush a journal with install, stage, backup, old/new manifest hashes, expected versions and state. Helper receives fixed transaction identity, not arbitrary file-operation arguments. It revalidates boundaries, journal and hashes, acquires the lock, waits on the actual parent process handle and rechecks for other instances/locks. Never elevate or kill another process.
4. Journal write-ahead intent before each mutation: `prepared -> moving_old -> old_moved -> moving_new -> candidate_installed -> health_pending -> committed`. Rename old root to the unique sibling backup; rename staged new root to the original root. If the second move fails, restore the old root immediately. Keep retry bounded for antivirus locks; do not schedule reboot replacement. Directory moves require the same drive; [Microsoft's MoveFileEx documentation](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexa) also shows why cross-volume copy/delete flags are unsuitable for this contract.
5. Run the installed new executable's offline self-check with a timeout and transaction nonce. Then launch it with a health mode that creates an empty session, initializes the GUI/event loop and acknowledges expected version/manifest/nonce over a private channel. Do not open or migrate a real project or save preferences while checking. Helper remains alive until success/crash/timeout. Check nonce and process identity, not a stale marker file.
6. Failure: after candidate process exit, move the failed candidate aside inside this transaction, restore backup to original root, and offer/relaunch the previous version into an empty session with recovery information. Do not overwrite user projects. Keep diagnostic journal and files if rollback meets a lock error; show the runnable backup executable and a deterministic Resume recovery action.
7. Success: persist `committed` only after self-check, GUI acknowledgment and a short bounded startup observation complete. Keep one previous version until a later deliberate successful app launch/cleanup acknowledgment; cleanup can fail harmlessly and be retried. Never delete the only known runnable package. Continued operation for arbitrary time is outside this startup-health promise.

Each journal update uses replace-after-flush and schema/nonce/path validation. Resume inspects actual existing trees and manifest hashes, not just the last recorded state; write-ahead states cover death between a rename and its completion record. On restart, pre-GUI recovery checks the installation's transaction index. Prefer rollback for any uncommitted/ambiguous candidate. Never delete a tree whose identity cannot be established.

Two directory renames are **not** an atomic multi-directory transaction. Power loss between them can leave the usual executable path temporarily absent. The separately retained helper and backup must be runnable directly and supply Resume recovery; show their exact paths before closing the old app and retain a recovery instruction file alongside them. Test this interruption explicitly. Scope excludes failed hardware, hostile local-admin tampering and filesystem corruption; do not promise universal power-loss durability from rename alone.

## Implementation boundaries and bounded build sequence

1. **Authenticated format and pure verification:** add descriptor/package schema, test fixtures and exact ownership rules; choose/review ZIP and signature libraries; add direct deps only as required. Extend `scripts/package.ps1`, `scripts/check-package.ps1`, workflow artifact/signing checks and notices. Tests reject wrong identity/key/signature, duplicate paths/JSON, traversal/link aliases, truncation and resource overflow. No GUI install button yet.
2. **Manual check/download:** a focused updater module owns release selection, origin policy, streamed staging and cancellation. Reuse serde/sha2 and worker/progress patterns. `src/shortcuts.rs`, `src/app.rs` menu/dispatch/messages/accessibility add Check for updates and release details. Test versions, flags, assets, offline/rate-limit/errors and pagination limits using local fixtures; no ambient token and no startup request.
3. **Recovery helper and close gate:** helper/recovery argument handling in `src/main.rs`; updater filesystem/journal module; registration via `src/lib.rs` as needed. Shared application close handling protects ordinary close and updater restart. Exercise all journal transitions, locks, disk/permission errors, cancellation boundary, worker draining and rollback with disposable synthetic package roots. No mutation under real owner folders.
4. **Package acceptance and docs:** use `scripts/gui-dev.ps1` and `scripts/check.ps1 -Local`; run packaged old-to-new update, forced self-check failure, GUI crash/timeout and killed-helper recovery on Windows. Verify source commit, executable paths, package hashes, all owned DLLs/notices, obsolete-file removal, stable shortcut path, retained rollback executable and unchanged project/cache/source/export fixtures. Update `docs/portable-readme.txt`, workflow/help and ticket acceptance evidence. macOS/Linux checking/link behavior remains manual until native integration and signing/recovery tests exist.
