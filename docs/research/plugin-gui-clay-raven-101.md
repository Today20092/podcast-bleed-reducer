# Clay and Raven plugin GUI addendum (101)

2026-10-27. Owner-requested extension of [ticket 101](../../.scratch/offline-supervised-editor/issues/101-plugin-gui-framework-and-vendor-stack-research.md) and the [framework comparison](plugin-gui-frameworks-101.md). Primary repository documentation, small source/header reads and GitHub metadata only; no cloning, building, native host, framework installation, prototype or dependency change. Podcast work continues independently.

## Decision

**Neither library currently justifies replacing the working egui/nice-plug editor.** Clay is a credible permissively licensed layout component, but selecting it means supplying much of an editor toolkit. Raven is a broader permissively licensed GUI system with attractive documented features, but the reviewed API owns native windows and does not demonstrate the foreign-parent editor lifecycle required by a DAW. Its early API, shared runtime and Rust callback lifetime conventions add integration work.

Keep fixing current layout, font coverage, clipping and interaction issues. If those reveal a specific toolkit blocker, the previously identified **nice-plug-iced** screen remains a smaller comparison: its actual plugin adapter exists, targets the same Iced 0.14 generation as the desktop and nice-plug-core ^0.4.2, and preserves the existing Rust format/DSP layer. This is an integration-cost judgment, **not a RAM/FPS or visual-quality ranking**.

## Rust boundary, ownership and threading

Clay's [official Rust-binding pointer](https://github.com/nicbarker/clay/blob/e6cc36941ab2af5d81107617039d6f527a1c660b/bindings/rust/README) directs users to **clay-ui-rs/clay**, package `clay-layout`. The reviewed binding [commit c7fadc915144a513476598a27b126cbe53a0b843](https://github.com/clay-ui-rs/clay/commit/c7fadc915144a513476598a27b126cbe53a0b843), dated **2026-08-09**, declares package 0.4.0 and optional raylib/Skia renderers. It offers Rust layout scopes/lifetimes, not an existing nice-plug editor. Its [source](https://github.com/clay-ui-rs/clay/blob/c7fadc915144a513476598a27b126cbe53a0b843/src/lib.rs) owns arena memory in std mode and borrows rendering data; C callback/context rules still apply. Do not pair arbitrary header/binding revisions: current Clay `Clay_EndLayout(float deltaTime)` differs from the binding's reviewed no-argument call. This demonstrates the need for a matched vendored API, not a proven failure of the published crate's bundled C version.

The [Clay C header](https://github.com/nicbarker/clay/blob/e6cc36941ab2af5d81107617039d6f527a1c660b/clay.h) uses a current-context pointer and callback configuration; it does not establish concurrent reentrancy. Serialize layout/context selection on the editor thread and retain arena/text/image/custom-command data for the required frame lifetime. Do not put layout or callbacks on the audio thread. The binding was not safety-audited or compiled here.

Raven includes its own [Apache-2.0 Rust binding](https://github.com/oscar-soirey/Raven/blob/abed7e6a695524d41ec73b5e29b46343d5293cb3/bindings/rust/README.md), `raven-gui` 0.1.0. It links a separately built native library and exposes the raw `unsafe` C API with a few helpers. [Binding source](https://github.com/oscar-soirey/Raven/blob/abed7e6a695524d41ec73b5e29b46343d5293cb3/bindings/rust/src/lib.rs) documents `action_bind` closures as living until program termination and transfers their boxes through `Box::into_raw`; it is not a complete per-editor RAII/unbind/lifetime layer. Plugin unload, panic containment, callback unregistering and native-library ABI/version ownership must be designed explicitly.

Raven's [core API](https://github.com/oscar-soirey/Raven/blob/abed7e6a695524d41ec73b5e29b46343d5293cb3/include/raven/raven_core.h) makes the `Rinit` caller the UI thread except for documented thread-safe operations. [Context implementation](https://github.com/oscar-soirey/Raven/blob/abed7e6a695524d41ec73b5e29b46343d5293cb3/src/core/context.c) has a library-global `g_rvn`, rejects repeated initialization, supports a render thread and chooses default workers from CPU count minus UI/render threads. A plugin adapter would need an explicit multi-instance/shared-runtime lifecycle and bounded worker policy. Custom widget paint and viewport rendering have different callback-thread contracts; passing mutable DSP state directly to either is unsuitable.

## Memory and maturity implications

Clay's caller-provided arena makes **layout allocation capacity** explicit, with sizing/error APIs. It does not bound font caches, waveform data, GPU resources or host memory. Raven's [allocator/arena implementation](https://github.com/oscar-soirey/Raven/blob/abed7e6a695524d41ec73b5e29b46343d5293cb3/src/core/memory.c) includes dynamic allocation and growable arena blocks; it is not Clay's fixed caller arena. Its source exposes allocator selection/statistics and configurable worker/render settings. Those are useful controls to measure, not evidence of lower total RAM.

Do not reuse either upstream's microsecond-layout, binary-size or benchmark numbers as CleanSlate measurements. On this 32 GiB machine, native-library build cost, Vulkan/driver allocations, font/cache sizes, per-instance resources and default worker count matter more than a layout-only claim. Raven explicitly warns its public API can change; Clay's stable-looking version number does not remove integration/testing work. No comparative build/runtime measurements were made.

## Smallest worthwhile experiment, only after selection

**Clay:** a bounded one-panel layout experiment could render Clay commands through the existing baseview/OpenGL editor seam, preserving nice-plug and Rust DSP. Test an actual embedded window with two waveform placeholders, a resize-sensitive control row, one popup and one parameter gesture. Avoid adding an independent standalone event loop. Measure full frame/input behavior and total memory against the same egui screen, rather than comparing layout microbenchmarks.

**Raven:** the first experiment would have to be an **embedding/lifecycle proof**, before a redesigned screen: accept host HWND/NSView/X11 parent; open/close/reopen two simultaneous instances; keep DAW event-loop/thread ownership; verify renderer teardown and unload with no surviving callbacks/workers. Existing native-child viewport APIs do not satisfy this proof. Stop the experiment if it requires unsafe handle reparenting or process-global shutdown that disrupts another editor. Only after a supported seam exists should waveform/control/automation work be considered.

For either, future acceptance includes 100/125/150/200% DPI, font/glyph and keyboard/IME/focus tests, resize without clipping, accessible actions, repeated lifecycle tests and honest p50/p95/p99 frame/private-memory measurements under the shared resource guard. Do not migrate based on a screenshot. Current recommendation remains **egui fixes first; Iced plugin screen if a concrete alternative needs testing; Clay as a possible layout-only investigation; Raven deferred until parent-window/lifecycle evidence exists**.
